# ArmoniK Java SDK — Client

## Role of the Client SDK

The client SDK provides a language-friendly interface to interact with ArmoniK's control plane. It allows you to:

- Create and manage **sessions**.
- Define and submit **tasks**, optionally with dependencies.
- Create and manage **input and output blobs**.
- Monitor task progress and retrieve results.
- Use optional asynchronous callback mechanisms.
- Ensure consistent workflow semantics: retries, error propagation, idempotency.

---

## Entry Point: `ArmoniKClient`

The main entry point is `ArmoniKClient`, configured via `ArmoniKConfig` which describes:
- Endpoints
- TLS configuration
- Retry policy

The client opens up to 50 gRPC channels, that is HTTP/2 connections, to the control plane; set another number with `ArmoniKConfig.builder().withChannelPoolSize(n)`. Each channel carries one call at a time, so this is also the number of calls the client runs at once, across all its sessions; a call that finds every channel busy waits for one without blocking any thread, except the synchronous `openSession` and `getSession`, which block their caller until a channel is free.

One call per connection keeps a call unaffected when another connection is cut, for instance by an intermediate proxy, and avoids the problems shared HTTP/2 connections caused in the C++ and C# SDKs. It costs one TCP and TLS connection per call in flight, and caps the throughput at about the pool size divided by the duration of a call, network round trip included: raise the pool size for a distant control plane or many concurrent transfers.

Small inputs and payloads are created with their data in batched `CreateResults` calls, bounded by the control plane's `DataChunkMaxSize`, so a submission needs few calls whatever its number of tasks.

Use try-with-resources for automatic cleanup:

```java
try (ArmoniKClient client = new ArmoniKClient(config)) {
    // ...
}
```

**Available operations on `ArmoniKClient`:**
- Create a new `Session`
- Retrieve an existing `Session`
- Cancel a `Session`
- Close a `Session`

## Session Creation

Define a session with `SessionDefinition`, then submit it to get a `SessionHandle`.

`SessionDefinition` components:

| Component | Description |
|---|---|
| Partition IDs | Where tasks can execute |
| `TaskConfiguration` | Default configuration for all tasks |
| `BlobCompletionListener` | Callback when an output blob is `COMPLETED` or `ABORTED` |

---

## Blob Completion Listener

`BlobCompletionListener` is a callback interface for async result notifications. Register it in `SessionDefinition` to be notified when outputs complete.

```java
BlobCompletionListener listener = new BlobCompletionListener() {
    @Override
    public void onSuccess(Blob blob) { /* blob is ready */ }

    @Override
    public void onError(BlobError error) { /* handle error */ }
};
```

The callbacks run on a listener executor, never on the threads that complete the client's gRPC calls, so a callback may take time without slowing down submissions, uploads or downloads; it only delays the other callbacks. By default each client runs them on its own pool of one thread per available processor; supply another with `ArmoniKConfig.builder().withListenerExecutor(executor)`. An output counts as processed for `awaitOutputsProcessed()` once its callback has returned.

The client watches the outputs of a session by listing them with `ListResults`, as the C# and C++ SDKs do: every 100 ms at first, then less and less often, down to every 2 s, while no output changes, and not at all once none is pending. A completed output is downloaded into an array allocated from the size the listing reports.

The listener is optional. Without one, outputs are still watched, so `awaitOutputsProcessed()` waits for them, but their data is not downloaded. Use `BlobHandle.downloadData()` to fetch an output.

## Working with Blobs

| Type | Description |
|---|---|
| `InputBlobDefinition` | Data sent to workers |
| `OutputBlobDefinition` | Placeholder for expected results |
| `BlobHandle` | Reference to an already uploaded/downloaded blob |

Input data can come from:
- In-memory byte array
- File
- Custom source by implementing the `BlobData` interface

`SessionHandle` can also create session-scoped blobs directly.

## Task Submission

Create a `TaskDefinition` specifying:
- **Inputs**: `InputBlobDefinition` or `BlobHandle`
- **Outputs**: `OutputBlobDefinition`
- **Optional**: override `TaskConfiguration`
- **Optional**: `WorkerLibrary` for dynamic loading

Submit it to `SessionHandle`. This is **non-blocking** and returns a `TaskHandle` immediately.

To submit many tasks, pass them together to `SessionHandle.submitTasks(List<TaskDefinition>)`, which returns one `TaskHandle` per definition, in the same order. The blob metadata of all tasks is created in batched calls (at most 1000 blobs per call) and the tasks are submitted with one call per 1000 tasks, instead of one call of each kind per task. Input data is still uploaded blob by blob. Tasks sent in the same call succeed or fail together.

`submitTask` also batches: submitted tasks are buffered per session and sent together when the buffer holds 1000 tasks, or 100 ms after the first buffered task. `submitTasks`, `flushSubmissions()`, `awaitOutputsProcessed()` and `close()` send the buffer immediately. Configure it with `ArmoniKConfig.builder().withTaskSubmissionBatching(new TaskSubmissionBatching(batchSize, window))`, or disable it with `TaskSubmissionBatching.DISABLED` to send each task as soon as it is submitted.

Task and blob ids are known only once a task is sent. A loop that calls `submitTask` and then waits on `deferredTaskInfo()` or on the `deferredBlobInfo()` of an output therefore waits up to the batching window at each iteration. Submit the tasks with `submitTasks`, call `flushSubmissions()` before waiting, or use `TaskSubmissionBatching.DISABLED`.

A task is sent once the uploads of its inputs and payload are done. A task that could never run is not sent and its `deferredTaskInfo()` fails: when an upload of its inputs or payload fails, or when one of its inputs is an output of a task that was not submitted. The outputs of a task that is not submitted, for this reason or because the cluster rejected it, are reported to the session's `BlobCompletionListener.onError`, and `awaitOutputsProcessed()` does not wait for them.

## WorkerLibrary (Dynamic Loading)

`WorkerLibrary` describes a dynamically loaded worker library for task execution. It has three components:

| Field | Description | Example |
|---|---|---|
| `path` | Path to the artifact inside the zip | `"MyWorker.jar"` |
| `symbol` | Fully qualified class name | `"com.example.MyProcessor"` |
| `libraryHandle` | `BlobHandle` referencing the uploaded library zip | — |

## Typical Workflow

```
1. Create ArmoniKClient with config
2. Create SessionDefinition (with partitions, TaskConfiguration, listener)
3. Open SessionHandle
4. Define InputBlobDefinition and OutputBlobDefinition
5. Create and submit TaskDefinition
6. Wait for completion or react to BlobCompletionListener callbacks
7. Read output blobs
8. Close session and client
```

---

## Task Submission Flow (General)

1. The client creates a **session** to group related tasks.
2. Input data is uploaded as **blobs**.
3. The client defines one or more **task definitions**, each referencing:
   - input blobs (data dependencies)
   - expected output blobs
   - optional task configuration
4. Tasks are submitted to the control plane.
5. Workers execute tasks, read inputs, and produce outputs.
6. The control plane signals task completion.
7. The client retrieves output blobs or submits new tasks to continue the workflow.
